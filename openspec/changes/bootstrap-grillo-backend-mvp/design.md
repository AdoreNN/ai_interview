# Design

## Context

The repository currently contains OpenSpec scaffolding and an empty README, with no application code or established technology conventions. This is therefore a greenfield backend foundation. See `proposal.md` for motivation and the three capability specs for observable behavior.

The service needs HTTP authentication, relational persistence, ownership isolation, migrations, and a reproducible local runtime. The user requested two related application tables and a backend-focused container setup; frontend and ML runtimes are deferred.

## Goals / Non-Goals

**Goals:**

- Establish a small modular API that can grow into text interview and feedback features.
- Make the backend and PostgreSQL start together in a repeatable local environment.
- Keep credentials secure and authorization rules centralized.
- Represent enough session metadata for users to identify and reopen a configured interview.
- Keep the initial schema to exactly two domain tables.

**Non-Goals:**

- Persisting chat messages, prompts, answers, scores, or feedback.
- Integrating an LLM provider or running a separate ML service.
- Refresh tokens, password reset, email verification, OAuth, roles, or account administration.
- Session editing/deletion, full-text search, or pagination in the first iteration.
- Production orchestration, cloud infrastructure, or frontend delivery.

## Decisions

### Use FastAPI with a versioned REST API

Implement Python 3.12 with FastAPI, Pydantic settings/models, and Uvicorn. Domain routes live under `/api/v1`; the infrastructure probe remains at `/health`. Separate route, service, persistence, and configuration modules so future interview-dialogue logic does not accumulate in HTTP handlers.

FastAPI is selected for typed request validation, generated OpenAPI documentation, and a low-friction path to future asynchronous ML calls. Django was considered but adds administration and ORM surface not required by this MVP; Flask was considered but would require assembling more validation and API-contract infrastructure.

### Use PostgreSQL and migrations behind SQLAlchemy

Use PostgreSQL 16, SQLAlchemy 2, psycopg, and Alembic. The physical domain tables are:

- `users`: UUID primary key, normalized unique email, password hash, and creation/update timestamps.
- `sessions`: UUID primary key, non-null `user_id` foreign key to `users.id`, title, target position, constrained experience level, status, and creation/update timestamps.

The table is named `users` rather than `user` because `USER` has special meaning in SQL; it still represents the requested user entity. `sessions.user_id` is indexed for owner-scoped queries. Email uniqueness is enforced by the database after normalization. The `sessions` status starts as `created` and is represented with an explicit constrained value that can be extended when dialogue execution is introduced.

SQLite was considered for minimal setup, but PostgreSQL better matches a containerized, multi-user service and provides production-like constraints. Storing session configuration as an opaque JSON document was considered, but explicit columns provide validation and discoverability for the small stable field set.

Alembic's technical version table is not an application/domain table and is allowed in addition to the two requested domain tables.

### Use stateless short-lived bearer authentication

Hash passwords with Argon2 and never return the hash. Issue signed, short-lived JWT access tokens whose subject is the user UUID; configure signing secret and token lifetime through environment variables. A shared dependency validates the token and loads the current user for all session routes.

Refresh tokens were considered but would require revocation/storage policy and extra persistence beyond the requested baseline. Server-side sessions were considered but would add a session/token table or cache. Short-lived access tokens keep this iteration within two domain tables; refresh and revocation can be introduced as a later capability.

Authentication errors remain generic, and duplicate email handling maps the database uniqueness constraint to HTTP 409. Session lookups always include both session ID and current user ID, returning 404 for absent and foreign-owned records to avoid resource enumeration.

### Keep the API intentionally narrow

The initial routes are exactly:

- `GET /health`
- `POST /api/v1/auth/sign-up`
- `POST /api/v1/auth/sign-in`
- `POST /api/v1/sessions`
- `GET /api/v1/sessions`
- `GET /api/v1/sessions/{session_id}`

Sign-up and sign-in return the same authentication response shape. Session create/read responses use a shared public session shape. The title is provided by the user rather than generated by AI, avoiding an ML dependency while making chats identifiable immediately.

### Run backend and database as separate containers

Provide a multi-stage backend Dockerfile and a Compose file with `backend` and `db` services on an internal network. PostgreSQL stores data in a named volume and exposes a health check. The backend reads database and auth configuration from environment variables, waits on database health, runs migrations as an explicit startup step, and then starts the API. A checked-in example environment file documents required values without committing secrets.

Only these two containers are introduced now. Separate frontend and ML containers remain future additions because there is no corresponding application code or runtime contract yet.

### Verify behavior at API and persistence boundaries

Use pytest with FastAPI's test client and an isolated PostgreSQL test database. Cover successful and failing health, registration, sign-in, token validation, session creation/list/retrieval, cross-user isolation, and database constraints. Migration tests verify a clean database can upgrade to the latest revision. Container smoke testing verifies `/health` after Compose startup.

## Risks / Trade-offs

- [A single health route combines process liveness and dependency readiness] → Treat it as readiness for the MVP; split liveness/readiness probes if orchestration requires them later.
- [JWTs cannot be revoked before expiry] → Keep access-token lifetime short and add refresh/revocation design only when product requirements demand it.
- [No message table means a session cannot yet contain a conversation] → Keep the session API limited to metadata and add message persistence together with the interview-dialogue capability.
- [An unpaginated session list can grow large] → Accept the simpler contract for the MVP and add cursor pagination before high-volume usage.
- [Running migrations at every application replica startup can race] → Use one backend container for local MVP; production deployment must run migrations as a single release job.
- [Exact dependency versions and generated lock format can become stale] → Pin direct dependencies and use the project's chosen Python dependency manager consistently during implementation.

## Migration Plan

1. Add backend packaging, configuration, and container files without exposing a public deployment.
2. Add the initial Alembic migration for `users` and `sessions` and apply it to a clean PostgreSQL instance.
3. Start the database and backend containers, then confirm the readiness probe and OpenAPI schema.
4. Run automated API, ownership, and migration tests before integrating a frontend client.

Rollback for this greenfield change is to stop the new services and remove their deployment. In local development, the named database volume may be retained for retry or explicitly removed by the operator; no automated rollback deletes persisted user data.
